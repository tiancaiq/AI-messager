## Current production seam

- `packages/contracts/src/skills.ts` remains the shared strict Zod runtime schema. `SkillDefinition` has `id`, name/description, languages, situations, intents, actions, use/exclusion guidance, principles/avoidance, compatibility/conflict ID lists, positive integer `version`, and `ACTIVE | INACTIVE` status. `SkillContext` carries fixed action, intent/tags, language and draft/ambiguity flags. `CommunicationPlan` carries `SELECTED | NONE | FAILED`, at most four ID/version references with reasons, and bounded composed guidance.
- The approved manifest currently allowlists **21 ACTIVE version-1 definitions**: 14 universal atomic functions, three English modifiers, and four Chinese modifiers. Candidate skills and playbooks remain outside production. This count is a snapshot, not an architecture invariant.
- `packages/skills/definitions/approved-manifest.yaml` identifies each authoring record by stable ID, relative source path and record digest. One YAML record per definition is validated by private `packages/skills/authoring/` tooling; only approved runtime `definition` fields are projected into `src/generated/approved-registry.ts`. `src/registry.ts` validates/freezes the projection and exports `initialSkillRegistry`. Runtime does not load YAML, examples or authoring metadata.
- The public selector is unchanged: `createSkillEngine(input).select(context): CommunicationPlan`, with a validated `registry` property. The AI boundary is `CommunicationSkillPlanner.plan(context): CommunicationPlan`; the default planner calls the flat engine. Selection filters `ACTIVE`, language, action and intent/situation tags, ranks by fixed scores, resolves declared conflicts and selects at most four. `NONE` is valid. There is no production domain-scoped selector API yet.
- Runtime approval is distinct from examples. Current records use `INHERITED` only when their exact definition digest matches the frozen baseline; a changed definition needs explicit reviewed `APPROVED` metadata, while `DRAFT` is excluded. All 210 structured canonical examples remain `PENDING_HUMAN_REVIEW` and outside runtime/prompts. A path or example-only edit does not itself change runtime version or approval. Stable IDs and positive integer versions are present, but rename/deprecation aliases and a complete migration policy are not yet defined.
