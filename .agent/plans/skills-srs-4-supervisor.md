## Supervisor judgment, output and deterministic validation

Prompt the model to test, **for each candidate**, whether its job materially improves HOW the fixed user intent is communicated **without changing WHAT was decided**. It must inspect prerequisites, explicit negation, source ownership, thread resolution, present status versus future estimate versus coordination, and conditional coexistence. It may select several distinct supported jobs but must minimize redundant selections. No candidate may introduce a fact, motive, deadline, certainty, responsibility, apology, refusal reversal, continuing limit, or next step that the user did not support. Wording `NONE` means no supplied candidate materially helps, not low cosine similarity. Structural `NO_REPLY_NEEDED`, `SUGGEST_ACTIONS`, and `ASK_CLARIFICATION` bypass model supervision and report `STRUCTURAL_EMPTY`; do not relabel them `SUPERVISOR_NONE`.

Define a **private Zod-first** root-object wire schema. The model emits **exactly one** categorical decision for each supplied candidate and no chain-of-thought, free-form rationale, prose guidance, probability or uncalibrated `confidence`. Suggested shape:

```ts
type WireJudgment = {
  candidateDecisions: Array<{
    skillId: string;
    decision: "SELECT" | "REJECT";
    reasonCodes: ReasonCode[]; // 1–3 closed codes
    evidenceRefs: string[];    // 0–3 validated source:ordinal refs
  }>;
};
type SkillSelection = {
  status: "SELECTED" | "NONE" | "FAILED";
  selectedCapabilities: Array<{
    skillId: string;
    profileRevision: number;
    selectionReasonCodes: ReasonCode[];
  }>;
  candidateDecisions: WireJudgment["candidateDecisions"];
  failureCode?: "MODEL_OUTPUT_INVALID" | "PROVIDER_FAILURE" | "INPUT_TOO_LARGE" | "BINDING_DRIFT";
};
```

The **validator**, not the model, derives `SELECTED`/`NONE` from decisions; `FAILED` is produced only by transport, schema, binding or deterministic validation failure. `NONE`/`FAILED` contain zero selected IDs. A failure is **not** a correct `NONE`. Selected capabilities are sorted by stable ID for output; any future planning order is separate. Freeze a **0–4 ATOMIC capability** budget, matching production's current upper bound while excluding modifiers from the SRS-4 budget. The exposed labels have at most two required skills per positive case, so four is a safety ceiling, not a recall target. Do not tune it against the protected challenge.

Closed general reason codes (not one per skill):

| Positive | Rejection |
| --- | --- |
| `DIRECTLY_SUPPORTED`, `DISTINCT_SUPPORTED_JOB`, `COMPLEMENTS_SELECTED` | `PREREQUISITE_UNSUPPORTED`, `EXPLICITLY_NEGATED`, `OWNERSHIP_MISMATCH`, `WRONG_TEMPORAL_ROLE`, `REDUNDANT_WITH_SELECTED`, `CONFLICTS_WITH_SELECTED`, `NO_MATERIAL_JOB`, `INSUFFICIENT_EVIDENCE` |

An earlier thread is called resolved **only with positive visible evidence**; otherwise use `INSUFFICIENT_EVIDENCE` rather than falsely asserting no history. For explicit negation, cite its user-owned source. A select decision needs a positive code and a valid supporting evidence ref; an OTHER/UNKNOWN-only ref cannot establish a user-owned decision, responsibility or promise. Code/ref existence and source ownership are deterministic checks; whether the evidence truly entails the skill is measured by reviewed evaluation, not pretended to be solved by schema validation.

Post-validation must enforce: schema/root-object/closed codes; one decision for each **and only** each Top-10 candidate; unique IDs; selected IDs subset of frozen B Top 10 and ATOMIC lane; digest/revision match; valid evidence refs and reason-code polarity; no duplicate selected IDs; 0–4 bound; status invariants; fixed action unchanged; structural bypass; and bidirectional approved **explicit** conflicts if any exist in a future catalog. Current approved conflicts are empty, so no pair may be removed solely because it is a neighbor or `CONDITIONAL`. Do not synthesize missing dependency skills; no approved dependency field exists. On incompatible selected outputs, invalid refs, refusal, incomplete JSON, timeout, or provider error, return `FAILED` with a safe code; do not silently repair to a success or fall back to production selection. First experiment: **zero automatic model retries**, one response per intended observation; any rerun is an explicitly recorded repeat with the same frozen config.
