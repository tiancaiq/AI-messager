## Outcome

When the visible conversation contains an incoming message and no reliable compose-box draft, Message Coach decides whether a reply is warranted and what **user-supported reply goal** to pursue. It generates directly only when that goal is sufficiently supported, offers distinct choices when plausible goals materially differ, asks one question only when necessary, and can recommend no reply. A user can explicitly say what they want to accomplish in a new reply (for example, “ask what happened”) without that instruction being mistaken for draft text to rewrite. Every generated message remains reviewable and copy-only.

This milestone fixes the Agent decision entering the existing single-flow wording path. It does not claim that a new SkillPlan, extra agent, or different LLM message role can determine the user's intention.

## Scope and sequencing

**In scope:** a bounded, explicitly user-entered reply-direction seam; no-draft incoming-message action/goal policy; existing choice/clarification continuation; minimal desktop presentation needed to enter and review that direction; provenance-preserving Composer input; deterministic and opt-in quality evaluation. **Out of scope:** changing draft rewrite/completion quality, switching production to the shadow SkillPlan, changing the approved Skill catalog or top-k policy, B4/B4.5/B4.6/B4.7 historical dispositions, multi-agent orchestration, tool-calling, an extra provider call beyond the existing single wording call for a wording action, memory/identity/relationship retrieval, app-specific message integrations, automatic insertion/sending, a new backend content route, and an in-app Lab redesign.

- `packages/ai/src/coaching-policy.ts` handles reliable drafts first; without a draft, it recognizes narrow closing, invitation, and isolated-acknowledgment cases. Most other incoming messages default to `SUGGEST_REPLY` with `userIntent.value = "Respond naturally to the latest visible message."` This can choose wording before establishing what the user wants to communicate.
- `packages/ai/src/coaching-engine.ts` fixes the action before deriving production legacy skill guidance. The shadow assessment/selection/SkillPlan path remains comparison-only. `packages/ai/src/openai-coaching-adapter.ts` sends fixed policy metadata, selected intent, validated visible messages, draft, language, warnings, and `ComposerTask` as one user-role JSON payload under fixed app instructions. Captured `OTHER` text is evidence, not authority to instruct the Agent.
- `apps/desktop/src/renderer/App.tsx` and `capture-state.ts` support generated results, action choices, clarification continuations, retry, and explicit Copy, but no separate new-reply direction input. `apps/desktop/src/main/coaching.ts` owns the trusted request boundary.
- `packages/ai/src/coaching-policy.test.ts`, `coaching-engine.test.ts`, desktop state/UI tests, and synthetic coaching fixtures cover current behavior. B4 evaluations show factual/meaning problems in final wording, but those do not substitute for testing whether the **preceding reply decision** was right.

The product rule in [product behavior](../../docs/product-behavior.md) remains: infer first, generate when confident, offer choices when uncertain, ask only when necessary. [Privacy](../../docs/privacy.md) makes incoming text, draft, explicit direction, and generated text request-local sensitive content.

## Assumptions and decisions for review

1. A compose-box draft and an instruction to Message Coach are different sources. The Agent must not infer a user goal from `OTHER` text or treat “ask what happened” entered in the coach UI as a draft to polish. Explicit user direction can specify a new-reply goal; it cannot make an unsupported fact true.
2. Use the existing six `AgentAction` values. `SUGGEST_REPLY`, `SUGGEST_ACTIONS`, `ASK_CLARIFICATION`, and `NO_REPLY_NEEDED` are sufficient for the first slice. Do not add a model supervisor or `tool` role to solve goal ambiguity.
3. Keep the normal no-draft path within the existing provider-call budget. The first policy version is deterministic and conservative: when meaning or goal cannot be supported, prefer bounded choices or one material clarification over a guessed direct reply. A later model-assisted intent assessor would require its own measured quality/privacy/cost milestone.
4. Revised boundary fixture, approved 2026-10-17: an isolated “I don't want to speak with you, we are done” with no draft or explicit user direction should **suggest one brief, general regret/acknowledgment reply** for user review, rather than silently return `NO_REPLY_NEEDED`. It must not invent fault, ask a question, persuade, imply consent to continued contact, or send automatically. This inferred goal runs through the existing skill-guided wording path in one call. An explicit user direction such as “ask what happened” remains a separate path whose generated wording still needs human review; this revision does not approve a default question or change historical fixture policy.
5. The present `CoachingSelection` remains for offered-action/clarification continuation. A nullable, bounded `userDirection` field on `CoachingRequest` represents an explicitly entered **new-reply goal**. The strict contract rejects simultaneous selection and direction. A direction explicitly requests a new reply even if a visible compose draft exists; the draft is retained as an observation but excluded from this wording request and its user-owned factual support. The UI labels this override plainly.
6. `replyDecisionMode: "R1"` is an explicit, request-scoped migration switch sent by the current desktop UI. Historical B3.5/B4 fixture requests omit it and retain their frozen action policy for comparison. This is not a second skill pipeline or a long-lived user preference. Remove the legacy mode only after a separate fixture/evaluation migration review.
7. Preserve a request-local goal provenance distinction: explicit user direction, selected offered action/answer, evidence-supported inference, and unknown. Do not send raw extraction confidence or hidden reasoning as a fabricated goal. Do not persist a goal as memory or analytics.

## Contracts and data flow

```text
validated ConversationAnalysis (visible USER/OTHER/UNKNOWN observations, draft, confidence)
  + optional explicit coach-UI reply direction (not captured chat text)
  + optional existing choice/clarification selection
  -> Agent reply-decision policy (fixed action, goal, goal source, ambiguity)
     -> local choices / one clarification / no-reply: no wording call
     -> wording action: existing production skill selection
        -> ComposerTask with fixed action, source-qualified reply goal and constraints
        -> existing provider-neutral generator and per-candidate validation
        -> review/copy UI
```

Define any new cross-process field with a strict Zod schema in `packages/contracts` before producers/consumers. Extend the existing `CoachingRequest` and policy/ComposerTask seams rather than creating a second prompt or skill pipeline. A reply goal is a description of **what the user wants to communicate**, not a new fact, provider instruction, `taskPurpose` override, or orchestration command. The provider receives only relevant bounded visible context, the fixed decision/goal, and compact production guidance. Incoming `OTHER` text remains labeled conversation data; it is not promoted into an LLM instruction role. No `tool` message is needed.

## Risks, rollback, and limitations

- Conservative policy may offer choices more often than users want; quantify this against the reviewed fixture set rather than silently lowering the uncertainty bar.
- Lexical/deterministic policy cannot understand every nuance. Low confidence must remain visible; a later model-assisted decision stage needs separate evidence, budget, privacy, and cutover review.
- An explicit direction can still ask for a socially unwise reply. The Agent should preserve user choice without fabricating facts or ignoring a visible boundary; the boundary fixture requires human approval.
- The renderer's new direction input overlaps the concurrent UI & UX Lab. Integrate against one reviewed branch state; do not merge competing versions of the desktop flow.
- R1 does not resolve B4 Composer meaning/factual regressions or authorize SkillPlan cutover. A better goal can still produce an invalid message; existing guards and evaluation remain mandatory.
- Keep all text and screenshots request-local. No new logs, analytics, memory assertion, database row, provider tool, application API hop, or saved Lab history. Revert only R1-specific contract/policy/UI/Composer changes if its acceptance gate fails; preserve B4.7 and skill baselines.

## Requested R1 revision — inline draft instructions (2026-10-17)

The user rejected a separate Agent-chat/direction field as the intended interaction. The desired input is the text already visible in the messaging app's compose box. The Agent should distinguish communicative content from an instruction addressed to the coach, rather than asking the user to move the instruction into a separate field. This supersedes the separate coach-UI direction field in assumptions 1 and 5 as the desired end-state; those passages still describe the **current, uncommitted implementation**, not the approved future UI.

Example: incoming `Can you finish this?`; visible draft `no I can't finish write polite`. The intended interpretation is user-owned reply content `I can't finish this`, a style directive `polite`, and a fixed draft-rewrite action. `write polite` must not appear in the outgoing message. The incoming `OTHER` text is context, never an Agent instruction. No reason, deadline, promise, or ability may be invented. A candidate such as `I'm sorry, but I can't finish this.` is an illustration, not an approved live-model result.

The screenshot analysis contract currently returns an observation-only `draft.text` and explicitly forbids goal/intent inference. The deterministic R1 policy currently rewrites every reliable nonempty draft. Simply removing the new coach UI field would not separate an inline instruction; a phrase-specific substring rule would be too easy to misclassify as message content. The revised seam belongs **after** validated observation and **before** fixed action and skill selection. It should produce bounded, source-referenced communicative content and instruction, plus confidence/uncertainty, without treating the model's interpretation as a new fact or as permission to control orchestration. On uncertainty, preserve the visible draft and ask one material clarification rather than silently deleting words.

Required paired fixtures before implementation: mixed content plus directive (`no I can't finish write polite`), a normal draft containing similar words literally, an instruction-only draft whose reply stance is unknown, quoted/visible `OTHER` instructions, low-confidence extraction, Chinese equivalents, and a refusal whose strength must be preserved. Keep ordinary drafts on the existing path and the historical B3.5/B4 fixtures frozen. Remove the separate direction control only when the inline path meets these gates; retain contract compatibility until migration review. No new skill taxonomy, SkillPlan cutover, memory, persistence, or automatic sending is authorized by this revision.

**Open design gate:** reliable general interpretation likely needs a bounded Agent-side model interpretation step for suspected mixed drafts. That changes call count, cost, and privacy review; it must not be slipped into the normal path as a “small” parsing patch. The alternative is narrower deterministic recognition with an explicit uncertainty fallback, which cannot satisfy arbitrary natural-language instructions. Choose and evaluate the call topology before runtime edits. This revision does not itself authorize the separate future question of letting a model choose `NO_REPLY_NEEDED`; the current no-reply policy remains deterministic.

### Approved call topology and acceptance gate (2026-10-17)

The user chose **conditional model interpretation**. For a reliable nonempty draft on the desktop R1 path, a conservative local suspicion filter may request one additional, structured Agent interpretation call. The filter is a cost/privacy prefilter, never the authority that removes words. Validated model output must identify exact, nonoverlapping source spans for message content and a bounded coach instruction. The Agent verifies spans against the observed draft; only then does it derive an effective request for the existing fixed-action → production Skill selector → Composer flow. The original observation remains request-local and unchanged. Ordinary drafts, historical requests without R1, and low-confidence draft extraction make no interpretation call. A selected continuation carrying the same suspected draft is interpreted again so the original unseparated text cannot leak into its wording call. Incoming `OTHER` messages are labeled evidence only and cannot become instructions.

An interpreted mixed draft preserves only the message span as user-owned content; a validated style instruction reaches the existing Composer optional-style seam, never the draft text or factual-support set. A valid instruction-only style request with no established answer takes the existing choice/clarification path, not an invented stance. A validated instruction-only reply goal reuses `NEW_REPLY_GOAL` internally, with the draft removed; mixed content plus a reply-goal directive fails conservatively. An uncertain or invalid split returns a normalized error asking the user to edit the compose draft; a failed provider call returns a normalized provider error. Neither can send suspected directive text into Composer as a literal message. The interpreter uses the same trusted-desktop direct-to-provider topology, credential, timeout and `store: false` policy; the normal one-call wording path is unchanged, while suspected mixed drafts may use one interpretation call plus one wording call. No transcript, model reasoning, or provider payload is persisted or logged. The separate coach-direction UI is removed after deterministic integration tests pass; the old request field remains temporarily for contract compatibility.

Precommitted deterministic cases: trailing and leading mixed English directions; ordinary literal “write politely” content; instruction-only unknown stance; `OTHER` prompt injection; low-confidence draft; Simplified and Traditional Chinese style directions; refusal preservation; invalid/out-of-range/overlapping spans; provider failure; and historical no-R1 call-count parity. The acceptance gate is exact source support, action/skill/Composer separation, no leaked directive in any candidate, no unsupported commitment, full repository gates, and no live-provider quality claim without a separate human-reviewed run.
